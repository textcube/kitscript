# BUNTGAMES img2threejs 시각화 개발 기록

작성일: 2026-08-12

## 1. 목표

기존 BUNTGAMES 시각화 페이지의 평면적인 그래픽에 절차 생성형 Three.js 오브젝트를 결합한다. 단순한 3D 장식이 아니라 BUNTGAMES의 핵심 메시지인 **하나의 코어에서 여러 결과물이 생성되는 시스템**을 상징하는 인터랙티브 장치를 만드는 것이 목표였다.

## 2. 사용한 접근

- ImageGen으로 BUNTGAMES의 색상과 세계관을 반영한 기계형 코어 기준 이미지를 제작했다.
- img2threejs 파이프라인으로 이미지를 분석하고 부품·재질·반복 구조를 정의했다.
- 생성된 조형 스펙을 TypeScript 기반 Three.js 모델 팩토리로 변환했다.
- 브라우저 실행을 위해 esbuild로 단일 IIFE 번들을 생성했다.
- 기존 GSAP ScrollTrigger와 Three.js 런타임을 연결했다.
- 실제 브라우저 캡처를 반복 확인하면서 실루엣과 재질을 보정했다.

## 3. 핵심 시행착오

### 3.1 첫 번째 생성 모델은 완성품이 아니었다

최초 결과는 이미지의 구성 요소를 박스와 막대 형태로 분해한 **블록아웃**에 가까웠다. 일부 attachment 메타데이터가 프리미티브를 실린더 연결부로 바꾸면서 형태가 막대처럼 무너지는 문제도 있었다.

교훈:

- img2threejs의 자동 생성 결과는 곧바로 사용자에게 노출할 최종 모델이 아니다.
- 단일 이미지에서는 깊이와 후면 구조가 추정값이므로, 자동 생성 이후 실루엣 검수가 반드시 필요하다.
- 부품 수나 스펙 검증 통과 여부보다 첫눈에 하나의 물체로 읽히는지가 더 중요하다.

### 3.2 재질만 바꿔서는 구조 문제가 해결되지 않았다

흰색 블록으로 보이던 모델에 검정, 건메탈, 오렌지, 애시드 그린 재질을 적용했지만 부품 간 관계가 불명확해 사람 형상 또는 공중에 떠 있는 큐브처럼 보였다.

교훈:

- 색상은 위계를 강화할 수 있지만 잘못된 구조를 해결하지는 못한다.
- 중앙 코어, 외곽 프레임, 연결부, 모듈이라는 구조적 역할을 먼저 확정해야 한다.

### 3.3 장식 요소와 3D 오브젝트가 경쟁했다

기존 히어로의 큰 주황 원이 3D 코어 옆에 남아 시선이 분산됐다. 3D가 주인공이 된 이후에는 기존 장식의 역할을 다시 판단해야 했다.

해결:

- 히어로의 기존 `.orb` 요소를 숨겼다.
- 3D 코어가 오른쪽 영역의 단일 초점이 되도록 정리했다.

### 3.4 검수 기준을 중간 결과에 너무 관대하게 적용했다

초기 블록아웃을 기능적으로 작동한다는 이유로 완료에 가깝게 판단했다. 그러나 실제 캡처에서는 조형 완성도가 명백히 부족했다.

교훈:

- 렌더 성공과 디자인 성공을 구분한다.
- 최종 판단은 코드나 와이어프레임이 아니라 실제 브라우저 프레임으로 한다.
- 형체가 애매하면 기존 모델을 억지로 보정하기보다 화면용 프레젠테이션 리그를 새로 구성한다.

## 4. 최종 해결 구조

자동 생성 모델은 소스와 조형 기록으로 보존하되 화면에서는 거친 블록아웃을 숨겼다. 대신 동일한 기준 이미지와 스펙을 바탕으로 다음 구조의 절차형 hero rig를 제작했다.

- 검은 다면체 중앙 코어
- 애시드 그린 발광 내부 코어
- 서로 다른 축을 가진 다중 궤도 링
- 4개의 방사형 기계 모듈
- 8개의 오렌지/그린 잠금 클램프
- 내부 스트럿과 후면 플레이트
- 외곽 데이터 입자 궤도
- 중앙 `BUNT / GAMES` 발광 마크

이 구조는 더 이상 부품이 제각각 떠 있는 형태가 아니라 **하나의 동력 장치**로 읽힌다.

## 5. 모션과 인터랙션

- 마우스 X/Y 위치에 따라 코어 전체가 미세하게 궤도 회전한다.
- 외곽 링과 내부 링은 서로 다른 방향과 속도로 회전한다.
- 중앙 발광체는 주기적으로 맥동한다.
- 데이터 입자는 외곽 궤도를 따라 회전하며 크기가 점멸한다.
- ScrollTrigger 진행도에 따라 카메라 방향과 코어 회전이 변화한다.
- 스크롤 후반에는 방사형 모듈과 클램프가 바깥으로 분해된다.
- 화면을 벗어나면 IntersectionObserver가 렌더 상태를 제한한다.
- ResizeObserver로 캔버스와 카메라 비율을 동기화한다.

## 8. 빌드 방식

편집용 `coreScene.ts`를 수정한 뒤 프로젝트에 포함된 esbuild로 번들을 다시 생성한다.

```powershell
.\node_modules\@esbuild\win32-x64\esbuild.exe .\src\coreScene.ts `
  --bundle `
  --format=iife `
  --target=es2020 `
  --outfile=.\assets\img2threejs\buntgames-core-scene.js
```

실제 작업에서는 빌드용 스테이징 디렉터리를 사용하고, 검수한 번들만 `kitscript/home/assets/img2threejs`에 복사했다.

## 9. 현재 한계

- 기준 이미지가 단일 시점이므로 후면 구조는 절차적으로 추정했다.
- 중앙 로고는 CanvasTexture이므로 극단적인 측면 각도에서는 가독성이 낮아진다.
- 자동 생성 모델은 현재 화면에서 숨겨져 있으며 향후 세부 부품 라이브러리로 활용할 수 있다.
- 번들에 Three.js가 포함되어 파일 크기가 약 1.5MB이다.
- 모바일 저사양 기기에서는 그림자와 픽셀 비율을 더 낮추는 선택지가 필요하다.

## 11. 작업 원칙

- 자동 생성 모델은 출발점이지 최종 결과가 아니다.
- 첫 화면에서는 설명보다 실루엣이 먼저 읽혀야 한다.
- 모션은 장식이 아니라 구조와 기능을 설명해야 한다.
- 새로운 3D 요소를 넣을 때는 기존 2D 장식과의 시선 경쟁을 반드시 확인한다.
- 최종 완료 판단은 실제 브라우저 렌더 캡처를 기준으로 한다.
